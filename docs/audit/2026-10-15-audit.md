# P(-1) Hardening Audit — 2026-10-15 (shipped as 2.10.1)

Fourth P(-1) pass, run against the 2.10.0 tag after two toolchain language bumps
in a row: cyrius 6.6.9 → 6.6.20 (2.9.3) and 6.6.20 → 6.7.9 (2.10.0, the 6.7
language line). Done inline, by one reviewer, with no agent fan-out. Line
numbers below are the 2.10.0 tree's.

## Headline result

- **12 findings: 1 high, 5 medium, 6 low.** Nine are fixed in code, two are
  comment fixes (one superseded by a code fix), and one becomes a 2.11.0 roadmap
  item because it needs new public functions.
- **Every code fix has a regression test that fails on the 2.10.0 source and
  passes on 2.10.1.** Each was checked by reverting only that file. The two
  exceptions are noted (F11's partial-array free and F12).
- **The language bumps did not break majra, but they did move the ground under
  it.** The 6.7 line changes what existing code *means* (a lone `!` was silently
  dropped by the lexer before 6.7.3; new reserved words; unary `-`/`~` on a
  constant). Every item in cyrius's `ecosystem-migration.md` § 6.7.x was checked
  against the whole tree at 2.10.0, and none applies. 6.6.20's hashmap now
  rebuilds tables in place, which makes one unlocked walk in pubsub depend on an
  invariant nothing stated (F7).
- **No wire or API change.** Three internal structs grew by appended fields:
  the admin handle (32 → 48 bytes), both barrier states (+8 each) and the DAG
  job block (internal).

## High

- **[high] `src/relay.cyr:187-205, 229-233` — the RelayMessage refcount (2.9.0)
  raced across threads.** Every subscriber's consumer releases its own reference
  on its own thread, and the sender drops the creator's after unlocking, but
  retain and release were a plain load and store. Concurrent releases lost
  decrements (a leak), and a release racing a retain could drop a live count to
  0. Separately, `_relay_fan_out` retained *after* `chan_try_send` had published
  the pointer. A consumer that received and released in that window took the
  count from 1 to 0 and freed the message while the fan-out was still offering
  it to the next subscriber (use-after-free, then double free). **Fixed:**
  `atomic_fetch_add` for both, the retain moved before the send (with an undo on
  failure), and an over-release is refused instead of freeing twice. Test: four
  threads × 20,000 retain/release pairs must leave the count unchanged. The
  2.10.0 source fails it every run, with a wrong count or a crash.

## Medium

- **[medium] `src/ratelimit.cyr:469` — `sliding_window_check` failed OPEN for
  windows past 2^62 ns.** `window_ns * 2` wrapped negative (the sibling
  `sliding_window_evict_stale` already clamped it), so every check reset the
  window. An "N requests, ever" limiter spelled with `INT64_MAX` admitted
  everything: 6 of 6 against a quota of 3 on the 2.10.0 source. Separately,
  `elapsed * 1000` overflowed past ~9.2e15 ns. **Fixed:** both clamped, with a
  divide-first weight for huge windows.
- **[medium] `src/signed_envelope.cyr:160` — `signed_envelope_new` ignored
  `ed25519_sign`'s failure.** sigil re-derives the public key from the secret
  key's seed and refuses (-1, zeroed signature) when `sk[32..64]` does not match
  (the double-public-key oracle). majra's own check only ties `pk_ptr` to
  `sk[32..64]`, so a corrupt sk passed it, and the envelope shipped with an
  all-zero signature. **Fixed:** the -1 is checked. Test: key A's seed with key
  B's public half.
- **[medium] `src/dag.cyr:405` — `workflow_execute` leaked on every run.** The
  context, its map, the tier vectors, the in-degree map and every StepResult
  majra builds were all leaked; the context is never returned, so no caller
  could free them. The 2.10.0 source measures 856,800 bump bytes plus freelist
  growth over 300 runs, about 2.9 KB per run. **Fixed:** freelist-backed maps
  and vectors (a new `_majra_map_*` trio in `src/counter.cyr`, which frees the
  slot array a rehash supersedes), a per-job "majra made this result" flag, and
  teardown on every exit. Executor-returned results stay the executor's. Test:
  300 runs take no bump memory and carve no new freelist memory.
- **[medium] `src/barrier.cyr:150, 277` — both barrier sets keyed their map on
  the caller's name pointer.** This is the borrowed-key class 2.8.x fixed in
  pubsub, relay, heartbeat, ratelimit and fleet. A name built in a reused buffer
  re-keyed or lost its barrier: `BARRIER_UNKNOWN` on the 2.10.0 source.
  `barrier_complete` also leaked each state. **Fixed:** an owned name in each
  state (appended field), reused on re-create and freed on complete. Single-
  threaded states move to freelist vectors and are freed. Concurrent states stay
  allocated, because parked waiters read their flag.
- **[medium] `src/admin.cyr:249` — every admin request leaked bump memory.**
  sandhi's default-allocator helpers (`get_path`, `find_header`, `path_only`,
  `get_param`, `send_response`, `send_status`) and the JSON `str_builder` all
  allocate from the never-freeing bump heap, on every route including 400 and
  404. The endpoint is unauthenticated, so a request flood from anything that
  can reach it grows the process without bound: 315,200 bytes per 600 requests
  on the 2.10.0 source. **Fixed:** a growable arena allocator plus a mutex per
  admin handle (appended fields), the `_a` forms of every helper, and a reset
  after each request. The arena settles at its high-water mark, and the mutex
  keeps the public handler safe under a pooled server.
## Low

- **[low] `src/transport.cyr:154` —
  `conn_pool_with_circuit_breaker` keyed on the caller's endpoint pointer** and
  leaked the old breaker on re-registration. Freeing it instead would race
  `conn_pool_circuit_state`, which reads the breaker after unlocking. **Fixed:**
  the pool owns the key, and a re-registration reconfigures and resets the
  existing breaker in place.
- **[low] `src/redis_backend.cyr:174, 337` — `_resp_int` was lenient.** It
  skipped non-digits (`$1x2` read 12) and never detected overflow, so a 20-digit
  count wrapped negative and was returned as nil without poisoning the
  connection. The server's bytes were then parsed as the next reply. This is the
  class of the 2026 `redis-parser` multi-bulk-length reports. An array whose
  element read failed also leaked its own storage. **Fixed:** strict digits with
  an i64 overflow guard, `-1` as the only nil length or count, and the partial
  array's storage freed (its elements are untyped and are left alone, as
  `redis_array_free_shallow` leaves them). The partial-array free has no
  dedicated test.
- **[low] `src/postgres_backend.cyr:589, 764`** — `_pg_parse_row`'s
  allocation-failure path freed the cells but not the row vector, and
  `pg_init_workflow_tables` ran its two `CREATE INDEX` statements through
  `pg_exec`, which collects a rows vector that was then dropped. **Fixed,
  untested:** one needs an allocation failure, the other a live server.
- **[low, doc] `src/pubsub.cyr:369`** — `pubsub_publish` walks the pattern
  map's slot array unlocked. Since cyrius 6.6.20 a map with tombstones can be
  rebuilt *in place*, which would move a pattern behind the walk and drop a
  delivery. pubsub never calls `map_delete`, so no tombstones exist and the walk
  is safe. **Fixed:** the invariant is now stated where it matters.
- **[low, doc] `src/dag.cyr:272`** — `workflow_context_free` said full run
  teardown was "tracked on the roadmap". It was not. Superseded by the DAG fix.
- **[low, API → 2.11.0]** — returned blocks with no release function.
  `barrier_arrive` / `_force` and their concurrent twins, `relay_stats` and
  `fleet_stats` return freelist blocks (`fl_free` works, but nothing documents
  it). `hb_list_by_status`, `chb_list_by_status`, `hb_online`, `chb_online` and
  `storage_list_defs` return bump vectors, which cannot be freed at all. A
  patch adds no public function, so this is a roadmap item.

## Checked, no finding

- **Fixed-size buffers.** Every `var X[N]` in `src/` was checked against its
  largest write under cyrius-quirks #4 (locals are N bytes, globals N words). The
  error buffer holds 512 bytes for its 504-byte cap; redis argv uses 7 of 8
  slots; `fmt_int_buf` needs at most 21 of 24 bytes.
- **The 6.6.20 hashmap and majra's slot walks.** A new-key `map_set` can now
  move entries. No majra walk inserts into the map it walks, and relay inserts
  before it scans.
- **Allocator contracts.** `vec_push_a` still grows by alloc plus copy with no
  free, so `_majra_vec_push`'s own free is not a double free.
  `allocator_new`'s slot order matches majra's call.
- **The protocol surfaces** (RFC 6455 framing and handshake, RESP, PostgreSQL v3
  framing and dollar-quoting, encrypted IPC's nonce and replay design) hold up
  under re-review. The two known non-goals stand: WebSocket text frames are not
  UTF-8-validated (no bridge loop), and the handshake reads byte-at-a-time with
  no idle timeout (the consumer's accept loop owns `SO_RCVTIMEO`).
- **Ed25519 delegation.** sigil 3.13.11's verify rejects non-canonical S (RFC
  8032 §5.1.7) and small-order public keys.

## External research

Checked against advisories published since the last pass (2026-09-15):

- **libsoup CVE-2026-15711** — oversized WebSocket control frames. majra rejects
  any control frame over 125 bytes and requires FIN.
  ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2026-15711))
- **redis-parser CVE-2026-93435 / CVE-2026-97057, hiredis CVE-2026-88382** —
  unbounded nesting, an unvalidated multi-bulk length past 2^32, and unbounded
  aggregate allocation. majra caps depth (8) and array size (1M), and allocates
  as data arrives. The length-validation class is the low RESP finding above.
  ([OpenCVE 93435](https://app.opencve.io/cve/CVE-2026-93435),
  [OpenCVE 97057](https://app.opencve.io/cve/CVE-2026-97057),
  [ALAS 88382](https://explore.alas.aws.amazon.com/CVE-2026-88382.html))
- **PostgreSQL** — GO-2026-6172 (withdrawn; reading a declared size before
  bounding it) and CVE-2026-6477 (libpq `PQfn`). majra bounds a message at 16 MiB
  before allocating and has no function-call path.
  ([GO-2026-6172](https://pkg.go.dev/vuln/GO-2026-6172))
- **AES-GCM nonce reuse** (RUSTSEC-2026-0238, wolfProvider) and **Ed25519
  malleability** (forge CVE-2026-33895). majra's per-connection derived key with
  salted, role-split counters is outside the reuse class, and its signature
  verification is sigil's (see above).
  ([RUSTSEC-2026-0238](https://rustsec.org/advisories/RUSTSEC-2026-0238.html),
  [CVE-2026-33895](https://scout.docker.com/vulnerabilities/id/CVE-2026-33895))

- **`barrier_cycle` +13.6 % — flagged (over the 10 % line), accepted.** It is the cost of the
  barrier fix: a state's two set vectors now come from the thread-safe freelist (four `fl_alloc`s,
  ~270 ns) instead of the never-freeing bump heap, plus the name copy (embedded in the state block,
  which took it from +16 % to +14 %). The bench builds a throwaway set and barrier per iteration
  and never completes them, so it pays the allocation and never sees the release; before 2.10.1
  every completed barrier leaked its ~300 bytes for good.
- `relay_send` +2.2 % median: the atomic refcount (`lock xadd` per accepting subscriber).
- Everything else is within the run-to-run spread, including code this pass did not touch
  (`pattern_*` −5 %, `envelope_new` +1.6 % median / +7.5 % minimum).
