# P(-1) Hardening Audit — 2026-10-31 (shipped as 2.12.4)

Fifth P(-1) pass, run against the 2.12.3 tag before the 2.13.0 cut. Done
inline, by one reviewer, with no agent fan-out. Line numbers below are the
2.12.3 tree's.

## Method

- **The delta first.** `src/` had changed by 324 lines since the last pass
  (2.10.1): the 2.11.0 release functions, the 2.12.0 key cap and metrics
  dispatch, the 2.12.1 corrupt-TEXT fix. All of it was read line by line.
- **Then the tree, by defect class.** Map-key ownership at every `map_set`;
  bump-heap allocation on per-call paths; null handles on public functions;
  public entry points of the thread-safe types that skip their mutex.
- **Every fix has a test that fails without it.** Each was checked by putting
  the 2.12.3 code back in that one place (four mutants, below).

## Headline result

- **4 findings: 1 high, 1 medium, 2 low.** Three are fixed in code, all in
  `src/patra_queue.cyr`. The fourth needs a new public function, so it is a
  2.13.0 roadmap item.
- **The high one is data loss.** One `patra_queue` handle used from two threads
  lost committed jobs and undid completions, with every call returning success.
  It was not reachable from any test: no test shared a handle across threads.
- **No wire or API change.** No struct changed size.
- **External research found nothing new.** Each 2026 advisory class for the
  surfaces majra ships is already handled (see External research).

## High

- **[high] `src/patra_queue.cyr:318, 339` — `complete`, `fail` and the three
  counts ran outside the handle mutex.** Enqueue and dequeue take the handle's
  mutex; `_pq_update_status` and `_pq_count_where_status` did not. That mattered
  because of how patra serialises:
  - an enqueue holds a patra transaction open on the handle (BEGIN, `MAX(id)`,
    INSERT, COMMIT);
  - patra runs any statement on a handle with an open transaction **without**
    its statement mutex (`_stmt_lock` checks the handle's `DB_TX`);
  - the file lock does not help either: both threads use the same fd.

  So a `complete`, or even a count, from a second thread ran inside the first
  thread's transaction. Its `_pc_refresh` re-read the on-disk header into the
  handle over the uncommitted one, and the COMMIT then wrote the stale table
  directory back. Measured on 2.12.3 with a producer and a consumer on one
  handle, the producer pausing 1 ms between jobs, on ext4:
  - 93 of 300 committed jobs gone from the file in one run;
  - a job `enqueue` had returned an id for, missing in another;
  - a completion reported as done, back to running in a third.

  **Fixed:** both functions take the handle mutex, in the same order as
  enqueue and dequeue (handle mutex, then patra's locks).
  **Test:** `test_patra_queue_shared_handle`: a producer, a dequeue + complete
  consumer and a count poller on one handle, with a 30 s watchdog.
  - The 2.12.3 source fails it 10 of 10 runs: 203 of 300 enqueues refused,
    nothing delivered.
  - With only the count lock removed, it fails 10 of 10.
  - With only the `complete` lock removed, the handle deadlocks; the watchdog
    reports it in 30 s, 5 of 5.

## Medium

- **[medium] `src/patra_queue.cyr:241, 251` — one unreadable job blocked the
  whole queue.** 2.12.1 left a job whose TEXT payload cannot be read (a ref
  past the end of the file, a chain that will not read back) queued and
  undelivered. But dequeue selects the head row (`ORDER BY priority, id
  LIMIT 1`), so every later dequeue picked the same row and returned 0.
  Measured on 2.12.3: a good job enqueued behind a corrupt one, 5 dequeues,
  0 delivered.
  **Fixed:** dequeue moves an unreadable job to FAILED (status 3) and keeps
  searching. The UPDATE is keyed like the claim (`id`, `created_ns`,
  `status = 0`), so it touches that one row. A fail that matches nothing stops
  the search rather than spin. The job stays in the file, where it can be
  inspected, and is never delivered. A failed *query* still leaves every job
  queued, as before.
  **Test:** the 2.12.1 corrupt-ref test now enqueues a good job behind the
  corrupt one. It is delivered with its payload intact, and the corrupt job is
  counted as failed. Restoring the 2.12.3 behaviour fails 4 assertions.

## Low

- **[low] `src/patra_queue.cyr:42` — every `patra_queue_new` leaked the CREATE
  TABLE text.** `_pq_create_sql` assembled a constant with `str_builder` on the
  bump heap, which never frees. Measured: 448 bump bytes per open + close.
  **Fixed:** a literal. 40 bytes remain, neither majra's to free:
  - 32 is patra's WAL path (the path plus 5), filed in patra's repo by sit
    (`issues/2026-10-20-patra-open-keeps-its-wal-path.md`);
  - 8 is the handle's mutex cell. `mutex_new` has no release on any target, and
    on Windows it also initialises an SRWLOCK, so majra cannot allocate the
    cell itself.

  **Test:** 100 opens grow the bump heap by at most 64 bytes each. The 2.12.3
  builder fails it.
- **[low, API → 2.13.0] `src/namespace.cyr:60, 73, 93` — `namespace_topic`,
  `namespace_key` / `namespace_node_id`, `namespace_pattern` and
  `namespace_wildcard` return `Str`s built on the bump heap, with no release
  function.** A consumer that namespaces per publish leaks every call. This is
  the class 2.11.0 closed for the list and stats functions. Fixing it needs a
  new public release function, so it is roadmapped for 2.13.0 rather than
  patched here.

## Checked, no finding

- **The 2.10.1 → 2.12.3 delta.**
  - `storage_list_defs`'s slot walk matches the stdlib's own `map_values` (24-byte
    slot, state 1 = live).
  - The 2.11.0 release functions free exactly what their constructors allocate.
  - `fncall3` / `fncall4` have the same target arms as `fncall2` (Linux, macOS,
    agnos, Windows, cx). On each, arguments travel in registers with caller
    cleanup, so 2.12.0's "a callback may declare fewer parameters than its slot
    passes" holds.
  - The key cap's selection evicts exactly the excess, ties included.
  - Its LCG pivot defeats a crafted key order.
  - Its recorded slot indices stay valid because `map_delete` only writes a
    tombstone.
  - The last-seen stores sit under the limiter mutex, and both structs are
    allocated at their 2.12.0 sizes at their only allocation sites.
- **Map-key ownership.** Every `map_set` in `src/` stores an owned copy, or
  keys by a pointer the stored struct owns.
- **Per-call bump allocation.** Besides the two findings above:
  - the priority queue compacts its tiers, so they stay bounded;
  - pubsub's abandoned compaction buffers are deliberate and documented (a
    publish may be walking the old one).
- **Mutex discipline.** Every other public function of a thread-safe type that
  takes no lock reads one aligned word: a counter, a `map_size`, a field. That
  is atomic on both arches and only ever stale.
- **Null handles.** 164 public functions dereference their handle without a
  guard. That is the codebase's convention, not a gap: guards exist where a
  constructor can return 0 (`namespace_new`, `patra_queue_new`). The ratelimit
  module is inconsistent about it: its four count getters skip the guard the
  rest have. Recorded, not changed.

## External research

Checked against advisories published since the last pass (2026-10-15), and
older ones the 2.10.1 report did not record:

- **Netty CVE-2026-44890** — RESP length lines buffered without a cap. majra
  caps a line at 4,088 bytes, a bulk string at 64 MiB, an array at 1M entries,
  and nesting at depth 8.
  ([vuln.today](https://vuln.today/cve/CVE-2026-44890))
- **lib/pq CVE-2026-56873 / GO-2026-6172** — a backend frame allocated before
  its length is bounded. majra bounds every message at 16 MiB, in every phase,
  before allocating.
  ([Vulert](https://vulert.com/vuln-db/CVE-2026-56873))
- **Netty CVE-2026-33870, Jetty CVE-2026-2332** — request smuggling through
  CR / LF inside a quoted chunk extension. The admin endpoint parses no bodies,
  and `sandhi_server_run` serves one request per connection and closes it, so
  nothing smuggled is ever read as a second request.
  ([Corgea 33870](https://corgea.com/advisories/vulnerabilities/CVE-2026-33870),
  [Corgea 2332](https://corgea.com/advisories/vulnerabilities/CVE-2026-2332))
- **openssl-encrypt CVE-2026-74901** — a failed GCM tag falling back to
  unauthenticated CTR. majra's failed tag zeroes and frees the plaintext and
  returns an error; there is no fallback.
  ([Vulert](https://vulert.com/vuln-db/CVE-2026-74901))
- **Redis CVE-2025-67733, Dragonfly CVE-2026-47206** — RESP injection through
  Lua error replies, server-side. majra's half of that boundary is its client:
  every argument goes out as a `$len` bulk string, so CR / LF in a key cannot
  forge a command.
  ([Debian DSA](https://lists.debian.org/debian-security-announce/2026/msg00190.html),
  [CVE-2026-47206](https://cvefeed.io/vuln/detail/CVE-2026-47206))
- **libsoup CVE-2026-15711, redis-parser CVE-2026-97057, libpq CVE-2026-6477**
  — re-checked, unchanged since the 2.10.1 report.

## Upstream, filed

- **patra: a failed before-image read is logged as a zero page.**
  - Where: `src/wal.cyr:434`–`438`, which folds `nr < 0` into the past-EOF case.
  - Effect: an `EIO` on that read inside a transaction leaves an all-zero undo
    record, which a rollback or crash recovery writes over the live page. If
    that page is the header, the whole file is lost.
  - Reach: `patra_queue_enqueue`'s rollback path.
  - Filed 2026-10-31 as patra's
    `docs/development/issues/2026-10-31-wal-before-image-read-error-logged-as-zeros.md`;
    tracked under roadmap § Waiting on upstream.
