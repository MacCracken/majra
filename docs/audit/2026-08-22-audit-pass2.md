# P(-1) Hardening Audit, Second Pass — 2026-08-22 (shipped as 2.6.10)

The second pass required by [`CLAUDE.md`](../../CLAUDE.md) P(-1) step 10:
*"repeat if heavy — keep drilling until the pass is genuinely clean, not just
no errors."* [The first pass](2026-08-22-audit.md) returned 115 findings, and
2.6.9 rewrote roughly 7,000 lines repairing them. **Those repairs had never
been audited.**

**68 confirmed, 10 refuted.** Fifty are regressions introduced by 2.6.9 itself.

## The headline result

**Repairing 115 findings introduced 50 new ones.** That is the number worth
carrying forward. Every fix in 2.6.9 was individually reasonable and the suite
was green at every step, and the release still shipped a critical
security-control bypass, a memory-safety fix that was a verified no-op, a
self-deadlock, and a use-after-free it created out of a merely-racy read.

Three patterns account for most of it:

1. **A fix in one function, not its twin.** `_cbarrier_state_new` was fixed and
   `_barrier_state_new` was not. `chb_register` was fixed and
   `chb_register_with_telemetry` was not. The eviction path inside
   `relay_receive_ex` was fixed and `relay_evict_stale_dedup` was not.
   `map_keys` was removed from fleet, pubsub and relay and left in heartbeat.

2. **A fix that traded one bug for another.** Removing a leak by moving a
   buffer to module scope removed reentrancy. Bounding an allocation left the
   protocol desynced. Freeing a block turned an existing racy read into a
   use-after-free. Adding a mutex serialised a blocking read against every
   write on the same handle.

3. **A fix that was never verified to work.** The `fchmod` came after `bind`
   and did nothing at all.

## The critical

### The rate limiter fails open after an idle period

`src/ratelimit.cyr`. To stop fast polling discarding fractional credit, 2.6.9
replaced an unconditional clock reset with
`consumed_ns = refill * 1000000000 / rate_x1000`. But `refill` is bounded by
nothing — only `tokens` is clamped to burst — so a bucket idle long enough
overflows i64, `consumed_ns` returns NEGATIVE, and `last_ns + consumed_ns`
drives the clock **backward**. Every later call then sees a larger
`elapsed_ns`, refills to full burst, and returns allowed.

A permanent, silent bypass for that key. For a 1000 req/s limiter it needs
roughly 2.6 hours idle — a reconnecting tenant reaches it unaided. A security
control failing open, introduced by the fix for a starvation bug.

## Three that deserve naming

### The socket permission fix was a no-op

`src/ipc.cyr`. 2.6.9 called `fchmod(fd, 0600)` **after** `bind(2)`. `bind`
creates the filesystem inode from the sockfs mode masked by umask, and
`connect(2)` permission-checks *that* inode; `fchmod` afterwards touches only
the sockfs inode, returns success, and accomplishes nothing.

Reproduced directly under umask 022: fchmod-after-bind leaves the path at
**0755** while `fstat` on the fd reports 0600. fchmod-before-bind yields 0600.

This made 2.6.9 **worse than the gap it replaced**, because the module header
began asserting owner-only access. majra performs no peer-credential check, so
a consumer trusting that promise got a world-connectable endpoint on which
connecting *is* authenticating. There was no test on `ipc_bind` at all; there
is now, and it is mutation-verified.

### The RESP parser truncated ordinary Redis replies

`src/redis_backend.cyr`. 2.6.9 added `if (elem == 0) { return arr; }` to the
array loop. That function returns 0 for **three** different things: a read
failure, a nil bulk string (`$-1`), and the integer `:0`. So a rate-limiter Lua
script returning `*2\r\n:0\r\n:1\r\n`, or an `MGET` with a missing key,
came back as an empty array with its remaining elements still queued on the
socket — and the next command read those leftovers as its own reply, offsetting
the connection permanently. No hostile server required.

### Encrypted IPC could self-deadlock

`src/ipc_encrypted.cyr`. 2.6.9 put `encrypted_ipc_recv` under the same mutex as
`encrypted_ipc_send` and held it across `ipc_recv_frame` — a blocking `read(2)`.
A receiver waiting for a peer that sends nothing blocked every send on that
handle. For a request/response protocol that is a self-deadlock: the reply
cannot arrive because the request cannot be written.

## What pass 1 missed

Eighteen findings pre-date 2.6.9. The most serious is **SQL injection in the
PostgreSQL workflow API** — `pg_save_workflow_def`, `pg_get_workflow_def` and
`pg_delete_workflow_def` spliced caller-supplied strings into single-quoted
literals with no escaping.

Pass 1 found and fixed exactly this shape in `patra_queue` and did not look
here. That is a **lens gap, not a hard problem**: pass 1's `syscall-fs-sql`
lens was pointed at `patra_queue.cyr` and `main.cyr`, so `postgres_backend`'s
storage API fell between that lens and the wire-protocol one. Worth
remembering when scoping a third pass — the lenses partition the codebase, and
anything that falls between two of them is invisible to both.

## Tests that could not fail

The pass checked 2.6.9's own new assertions and found several tautologies —
they passed whether or not the fix was present, which is exactly how the first
audit's bugs shipped in the first place.

- `test_ws_framing` ran every assertion against `fd = -1`, where the guard path
  and the write-failure path both return -1.
- `test_resp_limits` asserted only that three constants were positive and that
  i64 addition wraps.
- Nothing anywhere exercised `transport_send` / `transport_recv`, so 2.6.9's
  `fncall2` → `fncall3` fix went unverified.
- Nothing exercised the new malformed-DAG rejection.

All four are now real, and the two most load-bearing are **mutation-verified**:
removing `_resp_poison` from the bulk path turns the RESP test red, and
restoring `fncall2` makes the transport test observe `len` as 4361233 — a stack
value — instead of 7.

## A verification failure of my own

While fixing the SQL injection, the insertion anchor for the escaping helper
was stale (an earlier commit had moved that comment to another file), so the
edit silently did nothing and `_pg_add_literal` was never defined. It compiled
to a trapping `ud2` and the suite **SIGILLed at exit 132** — which went
unnoticed because verification was reading `tail -1` of stdout rather than the
process exit status.

Suite verification now checks the exit code and requires a summary line. Worth
recording because it is the same failure mode as the tautological tests: a
check that cannot detect the thing it exists to detect.

## Refuted (10)

Good discrimination, and worth reading before re-filing any of them. The
verifiers refuted, among others:

- A claimed heap over-read in the `Sec-WebSocket-Key` scan — `memeq`
  short-circuits on the NUL written at `buf[total]`, so the scan is bounded.
- A claimed leak of the `QueueItem` in `mq_dequeue`'s cancelled path — freeing
  it would be a **use-after-free**, since that pointer is the one `mq_enqueue`
  returned to the caller, and the suggested `fl_free` on the job key would
  splice a bump-allocated pointer into the freelist.
- Claimed races in `patra_queue` — patra's parse state is thread-local, its
  writes take its own process mutex, and `_rs_materialize` snapshots TEXT
  payloads, so the described interleaving cannot occur.
- A claimed use-after-free in pubsub's slot-array walk — a grown-out entries
  array is *abandoned* by the bump allocator rather than freed, so the stale
  pointer stays valid memory.

## Not fixed in 2.6.10

- **`majra_admin_new`'s two-argument default.** The pass is right that
  defaulting to `ADMIN_TRACKER_CONCURRENT` leaves the guard unable to protect
  the caller it was written for. But the two tracker types are not
  distinguishable from their pointers, so the only available lever is the
  default — and flipping it to BASIC keeps incorrect callers safe purely by
  silently removing `/fleet` from every correct one. Verified concretely:
  flipping it turned two passing assertions red, and those assertions are the
  legitimate use. The real fix, a type tag at a common offset in both tracker
  layouts, touches every heartbeat accessor and is filed as 2.7.0 work.
- **Full `workflow_execute` teardown.** The tier vecs and StepResults are bump
  allocations and cannot be freed; only the context block was reclaimable.
  Structural, not patch-sized.
- **`_resp_buf` as a process-global line buffer.** Two threads reading two
  Redis connections interleave into one buffer. Pre-existing, and the fix is a
  per-connection buffer — a struct change.
- The deliberate deferrals from pass 1 stand unchanged: pubsub's blocking
  fan-out, PostgreSQL SCRAM + TLS, per-key ratelimit stats, parallel DAG tiers.

## Method

Six lenses, each re-checked by an independent adversarial verifier told to
default to *refuted* when uncertain — and, unlike pass 1, explicitly pointed at
`git diff dda5b72..HEAD` and told that its primary job was finding what 2.6.9
introduced rather than re-reporting what it fixed. The lenses were chosen for
the defect classes a large repair pass produces:

| Lens | Scope |
|---|---|
| `memory-ownership` | every `fl_free` 2.6.9 added — double-free, use-after-free, error-path frees |
| `locking` | operations 2.6.9 moved *under* locks, on the claim that they never block |
| `parser-arithmetic` | the new bounds checks, which are themselves a classic source of off-by-one and sign bugs |
| `loops-termination` | the retry and drain loops 2.6.9 added |
| `contracts-regressions` | behaviour changes and whether anything still depended on the old meaning |
| `under-covered` | modules pass 1 touched lightly, plus the test suites themselves |

## Performance

No regression against 2.6.9, measured over two trials: `circuit_state` 2ns,
`ratelimit_check` ~1.68µs, `pubsub_publish_nosub` ~183ns, `relay_send` ~1.51µs,
`heartbeat_100nodes` ~1.42µs, `pq_enqueue` ~589ns. The heartbeat sweep
rewrite removed the last per-sweep bump allocations without moving the
benchmark.

## Test surface

515 → 560 assertions. The additions are concentrated on the regressions
themselves and on making 2.6.9's own tests capable of failing.
